# QUANTGEN 정책 문서 자체 점검 파이프라인

이 파이프라인은 공개 소스와 정책 문서의 **검토 이후 변경**을 찾아 재검토할 문서를 알려준다. 법률 문구, 요금, 사업자 정보, 동의 사실이나 구현 상태를 임의로 확정하거나 자동 승인하지 않는다. 기준선에 기록된 검토는 코드와 문서의 정합성 검토이며, 공개 또는 법률 적합성 승인이 아니다.

## 실행과 결과

Python 3.11 이상과 표준 라이브러리만 사용한다. QUANTGEN 실행 환경, Flet·Qt 설치, 계좌 연결, API 키, 외부 네트워크가 필요하지 않다. 저장소 루트에서 실행한다.

```bash
python -m unittest tests.compliance_acceptance -v
python -m unittest tests.compliance_export_acceptance -v
python -m tools.compliance.check --check --report-dir .compliance-report
```

`.compliance-report/report.md`와 `report.json`에서 서로 다른 두 결과를 확인한다.

| 결과 | 의미 | 종료 코드 |
|---|---|---|
| 정합성 `PASS` | 20개 문서의 구조·메타데이터와 기록한 소스·문서 지문이 일치 | 기본 검사 0 |
| 정합성 `FAIL` | 문서 누락·변경, 소스 변경, 검토 기준선 불일치 등의 재검토 필요 | 1 |
| 공개 준비 `BLOCKED` | 사업자·계약·운영 증빙·문서 승인 등의 미확정 항목 존재 | 기본 검사와 별도; `--release`에서 1 |
| 공개 준비 `REVIEW_RECORDED` | 검사 대상 공개 증빙에 미해결 항목이 기록되어 있지 않음 | 실사·출시 승인·법적 적합성 인증을 의미하지 않음 |
| 불완전 검사 | 필수 파일·JSON·스키마·안전 경로가 잘못되어 검사 완료 불가 | 2; 별도 실패 보고서 작성 |

현재 제공본은 정합성 검사를 통과하더라도 공개 준비가 `BLOCKED`여야 한다. 실제 사업자 정보와 공개 승인 등이 미확정이기 때문이다. 출시 전 확인은 별도 명령으로 실행한다.

```bash
python -m tools.compliance.check --check --release --report-dir .compliance-report
```

## 변경이 생겼을 때

1. 보고서의 `changed_sources`와 `documents_needing_review`를 읽고 변경된 기능·전송·저장·자산·의존성을 확인한다. 화면 동작은 Flet, PyQt6, 실제 운영 서버를 나누어 시험한다.
2. `registry.json`이 가리키는 정책과 `양식`, [FACTS.md](FACTS.md), [RELEASE_GAPS.md](RELEASE_GAPS.md), [SOURCES.md](SOURCES.md)를 수정한다. 사업자·보유기간·계약 조건은 근거를 확보한 값만 반영한다.
3. 각 문서의 버전과 검토일 또는 기준일을 갱신한다. 코드 정합성 검토 완료만으로 `review-required`를 `approved`로 변경하지 않는다.
4. 변경 내용과 관련 문서·증빙을 실제로 검토한 뒤 검토자와 구체적인 검토 내용을 명시하여 기준선을 갱신한다. 아래 자리표시자에 실제 검토 주체와 검토한 범위를 입력한다.

```bash
python -m tools.compliance.check --refresh-baseline \
  --reviewed-by "검토자 또는 검토를 수행한 에이전트 이름" \
  --review-note "변경된 전송 경로와 개인정보 문서를 대조한 내용 및 미해결 운영 항목"
```

특정 문서만 재검토했다면 `--documents 1 6 8`처럼 번호를 지정할 수 있다. 나머지 문서에 남은 변경은 계속 실패한다. 최초 기준선, 문서 연결 대장 또는 공개 준비 프로필의 변경은 전체 20개 문서 검토를 요구한다.

```bash
python -m tools.compliance.check --refresh-baseline \
  --documents 1 6 8 \
  --reviewed-by "검토 주체 이름" \
  --review-note "AI 전송 범위 변경과 관련된 문서 1·6·8의 고지와 양식을 대조"
python -m tools.compliance.check --check --report-dir .compliance-report
```

기준선 갱신은 명시적인 기록 행위다. 검토의 독립성·권한·진실성을 자동으로 보증하지 않으며, `release-profile.json`의 미확정 값이나 발견 사항을 승인 상태로 바꾸지 않는다. 예시 문자열을 사실인 것처럼 검토자 이름이나 증빙으로 사용하지 않는다.

## 공개 문서 확정

20개 문서는 `문서 ID: QG-C01`부터 `QG-C20`, 버전, 검토일 또는 기준일, 상태를 첫 본문 절 이전에 표시한다. 허용하는 상태는 `review-required`, `approved`, `not-applicable`이다. 공개 승인은 문서 서두에 `승인자:`와 `승인 근거:`를 함께 기록해야 한다. 적용하지 않는 문서에는 `승인 사유:`도 필요하다. 양식 안에 적힌 예시 승인 문구는 메타데이터로 읽지 않는다.

공개할 정책 본문인 `정책 또는 구현 기준`에 `{{...}}` 또는 미확정 표시가 남으면 공개 준비가 차단된다. 실제 이용자가 작성하는 `양식` 절의 빈칸은 의도된 입력 항목이므로 이 검사에서 제외한다. `not-applicable` 문서는 사유·승인 주체·근거를 갖추고 공개 대상에서 제외한 경우에 한해 정책 템플릿의 빈칸을 허용한다.

`release-profile.json`은 공개할 사업자 정보와 18개 검토 영역, 실제 코드에서 발견한 8개 항목의 증빙을 관리한다. 사업자 연락처의 공통 이름은 `operator.support_email`과 `operator.support_phone`이다. `verified` 또는 `not_applicable`에는 근거 참조, 검토 주체, 완료한 한국시간 날짜, 판단 사유가 필요하다. `null`, `unverified`, 미래 검토일과 자리표시자는 차단 상태다. 계좌·신분증·키·이용자 요청서·계약 원문은 넣지 않는다. 보호된 운영 기록의 비밀값이 없는 문서 참조만 사용한다.

모든 문서 승인과 운영 증빙을 실제로 확정한 이후에는 **별도의 공개 증빙 검토 기록**이 필요하다. 아래 명령은 정합성 검사와 공개 증빙의 미해결 항목이 모두 해소된 경우에만 `publication-review.json`을 작성한다. 현재 제공본은 이 조건을 만족하지 않으므로 이 기록을 만들지 않는다.

```bash
python -m tools.compliance.check --record-publication-review \
  --reviewed-by "공개 증빙을 검토한 주체 이름" \
  --review-note "현 소스와 정책 및 실제 운영 증빙을 검토한 구체적인 내용" \
  --review-evidence "보호된 승인 기록 또는 공개 가능한 검토 근거 참조"
```

이 기록은 전체 소스·문서·연결 대장·운영 프로필의 지문에 묶인다. 그중 하나라도 바뀌면 이전 공개 검토 기록은 만료된다. 통상적인 `--refresh-baseline`은 이 공개 기록을 생성하거나 갱신하지 않으므로, 오래된 승인 표시가 남아 있어도 다시 공개 준비 통과로 바뀌지 않는다. 이 기록 역시 검토자의 진술과 근거 참조를 남기는 것이며 독립적인 인증이나 전자서명 검증이 아니다.

## 점검 범위와 연결 방식

`registry.json`은 사진의 20개 번호, 파일명, 소스 경로 glob을 연결한다. 기존 파일의 내용 변경은 연결된 문서를 모두 재검토한다. 어느 glob에도 맞지 않는 기존 파일의 내용 변경은 보수적으로 20개 전체에 연결한다. 감시 대상 파일의 **추가·삭제·이름 변경은 위치와 관계없이 20개 전체를 재검토**한다. 각 문서 지문에 감시 파일명 재고의 해시를 포함하므로 `core/**`처럼 넓은 glob 아래 새 파일을 넣어도 분류 검토를 생략할 수 없다. 기존 파일의 기능 의미가 달라지면 연결 대장도 수정해야 한다. 경로 연결은 개인정보 처리나 법률 적용을 추론하는 탐지기가 아니다.

- 공개 코드·설정·의존성 선언, UI, 배포 자산과 글꼴, 워크플로·점검기 자체를 추적한다. 신규·삭제·이름 변경도 지문 대조에 반영한다. 이름 변경은 삭제와 추가로 표시한다.
- 20개 문서는 내용 지문을 개별 기록한다. `README`, `FACTS`, `SOURCES`, `RELEASE_GAPS`, `PIPELINE` 보조 문서와 기존 공개 배포 검토 문서도 추적한다. 정책 근거의 변경이 조용히 누락되지 않는다.
- `.env*`, 숨겨진 자격증명 저장소, `paper_live`, `grokteam`과 최상위 보관 연구는 순회 전에 제외한다. 임의 JSON·JSONL 데이터 파일은 읽지 않는다. 공개 스키마와 명시한 달력·규칙 JSON, `package.json` 등 명시한 의존성 선언만 소스 대상으로 읽는다.
- `core/accounts`·`core/research`·`core/cache` 등 소스 패키지의 이름을 이유로 실행 코드를 누락하지 않는다. 신뢰하는 소스 패키지 안에서 계좌·토큰·캐시·holdout·frozen 등의 이름을 가진 디렉터리는 코드 확장자의 파일만 검사하며 실제 계좌·토큰·캐시 데이터는 열지 않는다. 패키지 바깥의 이러한 비공개 자료 디렉터리는 제외한다.
- 코드와 자산은 지문만 계산하고 실행하거나 보고서에 복사하지 않는다. 직접 참조 의존성 URL은 보고서에서 숨겨 인증정보 유출을 방지한다. 소스·문서 경로의 심볼릭 링크는 따라가지 않고 검사를 중지한다. 보고서 디렉터리와 보고서 파일의 심볼릭 링크도 거부하고 정상 출력은 임시 파일에서 원자적으로 교체한다.
- 텍스트의 CRLF는 LF로 정규화하고 바이너리 자산은 바이트 그대로 해시한다. Windows 체크아웃의 줄바꿈만으로 거짓 변경이 발생하지 않도록 한다.
- 기준선은 검토 시점 HEAD 식별자와 작업 파일 지문을 함께 기록한다. HEAD만으로 모든 작업 파일이 이미 커밋되었다고 주장하지 않는다. 기준선 파일 자체는 자기 참조 해시 대상에서 제외한다.

## GitHub 자동 실행

[compliance-review.yml](../../.github/workflows/compliance-review.yml)은 모든 PR, `main` 변경, 수동 실행, **매주 월요일 오전 9시 한국시간**에 실행한다. GitHub 예약 실행은 지연될 수 있으며 워크플로가 기본 브랜치에 있어야 예약이 활성화된다. 보고서가 바뀌었다고 정책 문구를 자동 수정하거나 댓글·메일을 발송하지 않는다. GitHub 알림은 이용자의 기존 설정을 따른다.

워크플로는 읽기 권한만 사용하고 계좌·운영 비밀을 전달하지 않는다. 테스트와 지문 검사를 수행하고 성공·실패 모두 작업 요약 및 30일 보관 보고서 artifact를 남긴다. 구조 오류나 잘못된 설정도 가능한 범위에서 실패 보고서로 남긴다. 체크아웃 자체가 실패하거나 보고서 경로를 쓸 수 없는 경우에는 작업 로그가 근거다.

### Word 문서와 양식 다운로드

테스트와 정합성 검사가 성공하면 별도 문서 생성용 `python-docx==1.2.0`을 설치하고 본문 Word 20개·작성 양식 Word 20개·양식 원본·통합 HTML·점검 결과를 생성한다. 이 문서 생성 단계만 패키지 설치 네트워크가 필요하며 정합성 검사 자체는 계속 오프라인이다. 공개 준비가 `BLOCKED`인 경우에도 검토용 문서를 받을 수 있지만, 정합성 실패 시 새 패키지를 배포하지 않는다.

업로드 전 파일 수·포함된 원본·MANIFEST 해시·Word 내부 ZIP·패키지 ZIP의 무결성을 검사한다. 업로드 대상은 exporter가 명시적 허용목록으로 만든 새 출력 폴더뿐이다. 원본 저장소나 운영 자료 폴더를 업로드하지 않는다. `source/.github`의 재현용 워크플로를 보존하기 위해 이 생성 폴더에만 숨김파일 포함을 허용한다. 내장 ZIP은 업로드에서 제외하여 실제 다운로드 ZIP에 문서·양식이 바로 들어가게 한다.

GitHub Actions 실행 화면의 **Artifacts**에서 `QUANTGEN_Compliance_20_Documents-실행ID-시도번호`를 누르거나 실행 요약의 다운로드 링크를 사용한다. 저장소 접근 권한이 있는 GitHub 계정으로 로그인해야 한다. 문서 패키지는 **30일간 보관**하며, 만료 후에는 새 성공 실행에서 다시 생성한다. `/workspace/...`는 실행 환경 내부 경로이므로 다운로드 링크로 안내하지 않는다.

```bash
python -m tools.compliance.verify --directory /tmp/quantgen-compliance-delivery
python -m tools.compliance.verify --archive /path/to/downloaded-package.zip
```

다운로드 패키지 검증기는 표준 라이브러리만 사용하며 파일을 추출하거나 원본 프로그램을 실행하지 않고 검사한다. 다운로드 artifact 생성은 문서의 공개 승인이나 제품 출시를 뜻하지 않는다.

소스 변경 후 문서를 확인하지 않은 PR은 `Document and source consistency` 검사에 실패한다. 이를 병합 필수 검사로 강제하려면 저장소 관리자가 GitHub 브랜치 보호 또는 ruleset에 이 검사를 추가해야 한다. 이 문서 묶음은 관리 설정을 자동 변경하지 않는다. PR 워크플로를 같은 PR에서 고칠 수 있다는 GitHub의 신뢰 경계도 존재한다. 정당한 검토가 필요한 곳에는 보호된 검토 정책과 담당자 승인을 함께 운영한다.

## 자동 검사가 확인하지 않는 사항

실제 배포 서버의 쿠키·로그·백업·접근권한, 계약 조건과 국외이전 국가·보유기간, 라이선스 구입, 법률 개정, 실사용 스크린리더·키보드 접근성, 개인정보 삭제 완료는 저장소 지문으로 입증할 수 없다. 정기 실행은 변경을 대조할 뿐 공식 법령 사이트나 운영 서비스를 자동 조회하지 않는다. [SOURCES.md](SOURCES.md)의 현행성, 운영 증빙과 수동 시험을 정기적으로 검토하고 결과를 기록해야 한다.

합성 테스트는 소스 추가·수정·삭제·이름 변경, Python·JavaScript 등의 의존성 선언·자산 변경, 문서 수정·누락·중복 절·깨진 로컬 링크, 메타데이터, 선택적 기준선 갱신, 비밀 데이터 제외와 소스 패키지 누락 방지, 심볼릭 링크와 안전한 실패 보고서, 미확정 프로필, 공개 검토 지문 만료, 의도된 양식 빈칸과 직접 URL 인증정보 가림을 시험한다. 제품 전체의 기능·접근성·보안 시험을 대체하지 않는다.
