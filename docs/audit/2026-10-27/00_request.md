### 3. 현재까지 확인된 사실
저장소 구성: ZIP에 core/quant/, core/ficc/, data/, ui/, tests/ 등 모듈이 존재한다. 따라서 파일별 단편 검토보다는 데이터 공급자→정규화→계산→UI 출력의 데이터 흐름을 추적하는 방식이 적합하다.
Python 문법 검사: 초기 점검에서 322개 Python 파일을 컴파일 검사했고 문법 오류 0건으로 보고됐다. 이는 실행 정상성이나 금융 계산의 정확성을 증명하지 않는다.
FICC·매크로 오프라인 자체 검사: 초기 점검에서 두 모듈의 자체 검사 결과가 ok로 보고됐다. 외부 데이터의 정확성이나 모든 경로의 정상 작동을 의미하지 않는다.
과거 테스트 요약: ZIP에 포함된 기존 기록에는 870건 중 PASS 749건, NOT_RUN 121건으로 기재돼 있다. 이는 기존 저장 기록이며 이번 감사 과정에서 870건을 새로 실행한 결과가 아니다.
현재 환경의 한계: 감사 실행 환경에 flet, yfinance, pandas-datareader가 설치되지 않아 전체 테스트 실행이 초기 단계에서 중단됐다. 외부 공급자와의 실시간 교차 검증 및 UI 성능 계측은 아직 완료되지 않았다.

### 5. 속도 감사 계획
앱 시작 시간과 각 화면 최초 로드 시간을 따로 측정한다.
화면별로 네트워크 요청 수, 요청별 지연시간, 응답 크기, 파싱 시간, 계산 시간, 렌더링 시간을 기록한다.
첫 실행과 같은 입력의 두 번째 실행을 비교해 캐시 적중 여부와 효과를 확인한다.
단일 자산 / 5개 / 20개 자산 등 대표 시나리오에서 총 시간을 측정한다.
API 호출 제한을 지키면서 중복 요청 제거, 캐시 TTL 개선, 병렬 처리 가능성을 검토한다.
성능 개선 전후에 같은 입력·같은 데이터로 결과가 동일하거나 허용 오차 내인지 회귀 테스트한다.

### 6. 데이터 정확성 감사 계획
각 데이터 시리즈의 출처, 원본 응답, fetch time, observation time, release/available time, 단위, 타임존을 기록한다.
날짜 중복·누락·역순, NaN/inf, 0 이하 가격, 잘못된 단위, 오래된 값, 비정상 급등락을 검사한다. 급등락은 자동 삭제하지 말고 경고와 검토 대상으로 둔다.
주식은 조정주가/비조정주가, 분할·배당, 거래일 캘린더를 명시한다.
금리·매크로는 관측일과 실제 발표일, 빈도, 단위(%, bp, 연율 등), 수정 발표 여부를 구분한다.
(-> 공급사필요)
FICC 상품은 할인곡선·포워드곡선·day count·calendar·business-day convention·volatility surface의 입력 및 출처를 확인한다.
BTC는 거래소, quote currency, 타임존, candle close 시각, 누락 봉, 거래소 간 가격 차이를 확인한다.
(-> FICC/BTC 모두 KIS에서 접근 가능한지, 안된다면 다른 공급사 중 최적화된 공급사 알아서 파악해서 딱 깔끔하고 센스있게 implement 할 것.)
구조화 상품은 독립 기준가격/해석 가능한 단순 사례와 대조하고, 입력 곡선·변동성·배당·조기상환 조건의 민감도를 검사한다.
예측 기반 지표는 학습/검증 기간 분리, look-ahead bias, survivorship bias, out-of-sample 성능, 예측 구간 보정 여부를 검사한다.

### 7. 다른 AI에 전달할 독립 검증 프롬프트
검토자는 독립적인 시니어 Python/퀀트 소프트웨어 감사자다. 첨부된 QUANTGEN 저장소 ZIP과 이 보고서를 검토하라.

목표:
1) 보고서의 각 발견사항을 실제 파일과 코드 라인으로 재검증하고, 사실/추정/오류를 구분한다.
2) 기능 완전성: README에 명시된 매크로, FICC, 주식, BTC/가상자산, 파생상품, 금융상품 스트럭처링, 예측 및 예측 기반 판단 지표가 실제로 구현되어 있고 UI 경로에서 호출되는지 추적한다.
3) 데이터 정확성: 공급자별 원본→정규화→캐시→모델 입력→UI 출력의 흐름을 그린다. 타임존, observation time vs fetched_at, 단위, 중복/누락, NaN/inf, 수정주가, 매크로 발표 지연, 합성 데이터 fallback, 캐시 만료/무효화를 점검한다.
4) 금융 계산: 핵심 공식과 단위·가정을 코드 근거와 함께 확인한다. 가능하면 독립 구현 또는 기준값과 비교한다. 근거 없이 금융 정확성을 인증하지 않는다.
5) 성능: 코드에서 의심 지점을 찾되, 실제 계측을 하지 않았다면 속도 문제를 확정하지 않는다. 실행 가능한 프로파일링 계획과 재현 명령을 제시한다.
6) 테스트: 테스트가 실제로 무엇을 보장하는지 확인하고, 미실행 테스트를 통과로 취급하지 않는다. 테스트 누락과 데이터 의존성을 구분한다.
7) 결과 형식: (a) 심각도 P0/P1/P2/P3, (b) 파일 경로와 함수/라인, (c) 재현 단계, (d) 기대 결과와 실제 결과, (e) 영향, (f) 수정안, (g) 회귀 테스트를 표로 제공한다. 모든 주장을 코드 근거로 뒷받침한다.
8) 수정은 사용자 승인 전 직접 수행하지 말고, 우선 감사 결과와 제안 패치만 제시한다. API 키/비밀정보를 출력하거나 요구하지 않는다.

중요: README 설명만으로 구현 완료를 판정하지 말고, 함수 존재만으로 정상 작동을 판정하지 말라. 확인하지 못한 사항은 '미검증'이라고 명시하라. 이 보고서의 주장도 맹목적으로 신뢰하지 말고 직접 검증하라.
