# `didm-score-v1` 제안 (초안, 미적용)

- 작성: DIDM_DEV 세션, 2026-11-24. **제안일 뿐이고 코드는 바꾸지 않았습니다.** `core/didm/llm/schema.py`는 `didm-score-v0` 그대로입니다. 적용은 메인이 DATA_SOURCE·QUANTGPT에 알린 뒤 (경계 규칙 5).
- 계기: 사전등록 5절 7번 "…스키마 버전, **보정 지도 버전**을 기록마다 남김"인데 v0 레코드에 그 필드가 없습니다. 지금은 `Assembled.calibration_version` 곁기록으로 들고 다닙니다 (메인 결정 2026-11-24).

## 1. 바꾸려는 것

| 필드 | 형식 | 이유 |
|---|---|---|
| `calibration_version` (추가, 필수) | 문자열. `uncalibrated` 또는 보정 지도 버전 (예: `iso-direction-<16자>`) | 사전등록 5절 7번. 보정 전 확률은 순위로만 쓰므로 (1절 A3) 레코드만 보고 구분할 수 있어야 함 |
| `judgement_version` (추가, 필수) | `didm-judgement-v0` | 어떤 판단 형식에서 조립됐는지. 판단 형식이 바뀌어도 옛 레코드를 가려낼 수 있게 |
| `schema_version` | `didm-score-v1` | 필드가 바뀌므로 새 버전 |

그대로 두는 것: 나머지 17개 필드의 이름·형식·규칙, 사건 유형 15개, 판단 형식 9개 필드.

## 2. 넣지 않기로 한 것

- 보정 전 방향 확률 (`raw_direction_probs`), `p_subject` 원값, `claim_status`: 판단 기록에 이미 있습니다. 레코드에 다시 넣으면 같은 값이 두 곳에 생깁니다. 판단 기록을 `record_id`로 찾을 수 있게 저장하는 쪽이 낫습니다 (저장 형식은 DIDM-6에서).
- 유형 확률 전체 (`event_type_probs`): 같은 이유.

## 3. 옮기는 법

1. `schema.py`에 v1 검증기를 더하고 v0 검증기는 남깁니다 (v0 레코드는 계속 읽힘).
2. `assemble_record`가 v1을 내고, JSON Schema와 적합성 예시를 v1용으로 하나 더 만듭니다.
3. 이미 저장된 v0 레코드는 다시 쓰지 않습니다 (지금은 저장된 레코드가 없음).

## 4. 판단이 필요한 것

- v1로 올리는 시점: Stage 1 정답 집합 채점을 시작하기 전이 좋습니다 (채점 결과가 v0·v1 두 형식으로 갈리지 않게).
- QUANTGPT 쪽 영향: 판단 형식은 그대로라 없습니다. DATA_SOURCE 쪽 영향: 레코드를 읽는 코드가 아직 없어 없습니다 (미검증: 메인이 두 세션에 확인).
