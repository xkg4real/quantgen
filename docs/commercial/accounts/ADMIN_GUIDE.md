## 0. 들어가는 길과 표시

### 0.1 들어가는 길 (모든 기능 공통)

1. AWS 콘솔에 로그인합니다. **2단계 인증(MFA)을 켠 로그인**으로만 들어갑니다.
2. 오른쪽 위 리전 이름을 봅니다. **Asia Pacific (Sydney)** 가 아니면 눌러서 **Asia Pacific (Sydney) ap-southeast-2** 를 고릅니다. 다른 리전에서는 풀이 보이지 않습니다. 서울 리전은 이 계정의 조직 정책에 막혀 있을 수 있습니다.
3. 위쪽 검색창에 `Cognito` → **Amazon Cognito** → 왼쪽 **User pools** → 목록에서 **quantgen-prod** 를 누릅니다.
4. 이름이 `quantgen-dev`인 풀은 시험용입니다. 실제 회원 작업은 하지 않습니다.

이 문서에서 "공통 경로"는 위 1~3번을 뜻합니다.

풀 안의 왼쪽 메뉴 (새 콘솔, 확인한 것만): **Users**, **Groups**, **App clients**, **Authentication methods**, **Sign-in**, **Sign-up**, **Message templates**. 묶음 제목(User management, Authentication 등)과 그 밖의 메뉴 이름은 미검증입니다.

CloudShell: 콘솔 위쪽 막대의 `>_` 아이콘입니다. 콘솔 버튼이 없는 기능(7절, 12절)은 여기서 명령으로 합니다. 열린 뒤 프롬프트에서 `aws configure get region`으로 리전을 보거나, 명령마다 `--region ap-southeast-2`를 붙입니다 (이 문서의 명령은 모두 붙여 두었습니다).

### 0.2 회원 상태 이름표 (Users 목록의 열)

| 화면 표시 | 뜻 | 관리자가 할 일 |
|---|---|---|
| **Unconfirmed** | 가입했지만 이메일 인증 코드를 아직 넣지 않음 | 7일 지나면 5절로 정리 (16절 매주) |
| **Confirmed** | 정상 회원 | 없음 |
| **Reset required** | 관리자가 비밀번호 재설정을 걸어 둠 (6절) | 회원이 "비밀번호 찾기"로 새 비밀번호를 정할 때까지 대기 |
| **Force change password** | 관리자가 만든 계정, 첫 로그인 전 | 우리 운영에서는 관리자가 회원을 만들지 않으므로 보통 없음 |
| **Enabled** 열 = **Disabled** | 정지된 계정 (위 상태와 별개의 열) | 4절 |

확인 상태: 상태 값 4개(UNCONFIRMED, CONFIRMED, RESET_REQUIRED, FORCE_CHANGE_PASSWORD)는 **확인**. 화면에 보이는 정확한 철자(대소문자, 띄어쓰기)는 **미검증** → Users 목록의 Status 열에서 확인.

## 1. 회원 목록 보기·검색

- **언제**: 특정 회원을 찾을 때 (요청 처리, 문의 답), 매주 점검 때.
- **누를 순서**
  1. 공통 경로 → 왼쪽 **Users**.
  2. 목록 위 검색 칸 왼쪽에서 찾을 속성을 고릅니다 (예: **email**).
  3. 값을 넣습니다. 검색은 **앞부분 일치**입니다. `kim`을 넣으면 `kim`으로 시작하는 이메일이 나옵니다.
  4. 이메일로 로그인하는 풀이라 **User name** 열은 긴 영숫자(UUID)입니다. 사람을 알아보려면 **Email** 열을 봅니다.
- **검색 가능한 속성** (**확인**): username, email, phone_number, name, given_name, family_name, preferred_username, sub, 상태(Status), 사용 여부(Enabled). 한 번에 **속성 하나**로만 거릅니다.
- **검색 안 되는 것** (**확인**): 사용자 정의 속성(`custom:…`). 그래서 "광고 수신 동의자 목록"은 12절 명령으로 만듭니다. 그룹 안 검색도 안 됩니다 → 그룹 화면의 회원 목록을 봅니다.
- **회원에게 생기는 일**: 없습니다 (보기만).
- **주의**: 목록 화면을 캡처해 채팅·Notion·GitHub에 올리지 않습니다. 이메일은 개인정보입니다.
- **확인 상태**: 검색 속성과 앞부분 일치 **확인** (ListUsers API 문서). 검색 칸의 화면 모양 **미검증**.

## 2. 회원 상세 보기

- **언제**: 요청 처리 전 본인 확인, 정지·삭제 전 대상 확인.
- **누를 순서**
  1. 1절로 회원을 찾음 → 파란 글자 **User name** 을 누릅니다.
  2. 보이는 것: 상태, Enabled 여부, 가입·수정 시각, MFA 설정, **User attributes** (email, email_verified, sub, 사용자 정의 속성 6개), 그룹 소속.
  3. 사용자 정의 속성의 뜻은 아래 표.

| 속성 | 뜻 | 예 |
|---|---|---|
| `custom:terms_ver` | 동의한 이용약관 버전 | `2026-12-01` |
| `custom:privacy_ver` | 확인한 처리방침 버전 | `1.11` |
| `custom:age14` | 만 14세 이상 본인 진술 | `Y` |
| `custom:consent_at` | 가입 동의 시각 (ISO) | `2026-12-01T10:00:00+09:00` |
| `custom:mkt_opt` | 광고성 소식 메일 수신 | `Y` / `N` |
| `custom:mkt_at` | 위 값을 바꾼 시각 | ISO 시각 |

- **회원에게 생기는 일**: 없습니다.
- **주의**: ① 비밀번호는 어디에도 보이지 않습니다. 관리자도 알 수 없습니다. ② 상세 화면을 여는 것도 관리자 작업 기록(CloudTrail)에 남을 수 있습니다 (`AdminGetUser` 등 관리 이벤트). 필요할 때만 엽니다. ③ 회원별 로그인 기록은 Essentials 요금제에서 보이지 않습니다 (0.3표 8번).
- **확인 상태**: 상세 화면으로 들어가는 길 **확인**. 화면 안 구역 이름은 **미검증** → 처음 열 때 구역 제목을 적어 주세요.

## 3. 가입 승인·거부 (쓰는 경우만)

**권장: 쓰지 않습니다.** 회원이 이메일 코드를 넣으면 가입이 끝나게 둡니다. 아래는 승인제를 원할 때만입니다.

- **언제**: 초대한 사람만 받는 비공개 시범 운영을 할 때.
- **누를 순서 (수동 승인 방식)**
  1. 설정: 공통 경로 → **Sign-up** → 이메일 자동 확인 설정 구역 → **Edit** → Cognito가 자동으로 확인하는 항목을 끔 → **Save changes**. *(구역·체크 문구 미검증. 문서상 이름은 "Cognito-assisted verification and confirmation")*
  2. 승인: **Users** → 회원 (상태 **Unconfirmed**) → **Actions** → **Confirm account** → 확인 창에서 확인.
  3. 거부: **Users** → 회원 → **Actions** → **Disable user access** → **Disable** → 다시 **Actions** → **Delete user** → **Delete** (5절과 같음).
- **회원에게 생기는 일**: 승인하면 바로 로그인할 수 있습니다. 거부하면 계정이 지워집니다. 자동 안내 메일은 가지 않는다고 봅니다 (미검증) → 필요하면 직접 메일.
- **주의**: ① **Confirm account**는 이메일 주인이 맞다는 확인이 끝난 경우만 누릅니다. ② 자동 확인을 끄면 이메일이 인증되지 않아 "비밀번호 찾기"가 안 될 수 있습니다 (미검증). ③ 다른 방법(허용 목록 Lambda)은 코드가 필요해 지금은 하지 않습니다.
- **확인 상태**: **Confirm account** 부분 확인. 1번의 자동 확인 끄기 문구 **미검증** → Sign-up 메뉴에서 "verification" 또는 "confirmation" 글자가 있는 구역.

## 4. 계정 정지·해제

- **언제 정지**: 부정 이용 의심, 만 14세 미만으로 밝혀짐, 처리정지 요청 (11절), 탈퇴 요청을 확인하는 동안, 삭제 직전 (5절).
- **누를 순서 — 정지**
  1. 공통 경로 → **Users** → 회원 이름을 누름.
  2. 오른쪽 위 **Actions** → **Disable user access**.
  3. 확인 창에서 **Disable**.
  4. 목록의 **Enabled** 열이 **Disabled** 로 바뀐 것을 봅니다.
- **누를 순서 — 해제**
  1. **Users** → 회원 → **Actions** → **Enable user access** → 확인 창 **Enable**.
- **회원에게 생기는 일**
  - 정지: 모든 기기의 로그인이 끊기고, 다시 로그인할 수 없고, 로그인 유지 토큰이 폐기됩니다 (**확인**). 회원에게 자동 알림은 가지 않는다고 봅니다 (**미검증**) → 필요하면 직접 메일.
  - 해제: 바로 다시 로그인할 수 있습니다 (**확인**).
- **주의**: 정지는 삭제가 아닙니다. 정보는 그대로 남습니다. 정지한 날짜와 이유를 처리 기록 (16.2절)에 남깁니다.
- **확인 상태**: 버튼 문구와 효과 **확인** (D11, AWS 회원 관리 문서). **소유자 시험 대상** (부록 C).

## 5. 계정 삭제 (정지 먼저)

- **언제**: 회원이 탈퇴를 원하는데 스스로 못 할 때 (11절), 인증 안 한 지 7일 지난 계정 (16절 매주), 만 14세 미만 확인, 3절 거부.
- **누를 순서**
  1. 공통 경로 → **Users** → 회원 이름을 누름. 이메일과 **sub** 를 한 번 더 봅니다 (다른 사람이 아닌지).
  2. **Actions** → **Disable user access** → **Disable** (먼저 정지). 콘솔은 정지하지 않은 회원의 삭제를 막아 둡니다 (re:Post 답변 기준, 공식 문구 미검증).
  3. 다시 **Actions** → **Delete user**.
  4. 확인 창에서 **Delete** *(확인 창에 이름이나 문구를 입력하라고 하는지는 미검증)*.
- **회원에게 생기는 일**: 계정과 모든 속성이 **즉시, 되돌릴 수 없이** 지워집니다. 같은 이메일로 다시 가입할 수는 있습니다 (새 계정 고유번호 sub).
- **주의**
  1. 삭제 전 본인 요청인지 확인합니다 (11절 2단계).
  2. CloudTrail 기록에는 그 회원의 sub가 남습니다. 1년 보관 기록이라 지우지 않습니다. 회신에 이 사실을 적습니다.
  3. 내보낸 파일(12절)에 그 회원이 있으면 그 파일도 지웁니다.
  4. 여러 계정 정리 (예: 인증 안 한 계정): 12절 3번 명령으로 목록을 먼저 만들고, **하나씩** 확인하며 지웁니다. 한꺼번에 지우는 스크립트는 쓰지 않습니다.
  5. 잘못 지웠을 때: 17절 E.
- **확인 상태**: **Delete user** **확인**. "정지 먼저" 순서 **부분 확인**. **소유자 시험 대상** (부록 C).

## 6. 비밀번호 재설정

- **언제**: 회원이 해킹을 의심한다고 알려 왔을 때, 비밀번호 유출이 확인됐을 때. 그냥 비밀번호를 잊은 회원은 관리자가 할 일이 없습니다 → 웹의 **비밀번호 찾기** 를 안내합니다.
- **누를 순서**
  1. 공통 경로 → **Users** → 회원 → **Actions** → **Reset password**.
  2. 확인 창에서 재설정을 누릅니다 *(확인 창 버튼 문구 미검증)*.
  3. 목록의 상태가 **Reset required** 로 바뀐 것을 봅니다.
- **회원에게 생기는 일**: 지금 비밀번호가 **바로 막힙니다**. 회원 이메일로 확인 코드가 가고, 코드는 **1시간** 유효합니다 (**확인**). 회원은 웹의 비밀번호 찾기 화면(웹사이트 요청 ACC-4)에서 코드와 새 비밀번호를 넣습니다.
- **주의**: 관리자가 직접 비밀번호를 정해 주는 명령(`admin-set-user-password`)은 **아래 6.1의 경우에만** 쓰고, 언제나 **임시**(`--no-permanent`)로만 씁니다. 관리자가 영구 비밀번호를 정하면 회원 비밀번호를 알게 됩니다.

### 6.1 이메일 MFA 회원이 비밀번호를 잊었을 때 (소유자 결정 2026-11-19)

이메일 MFA를 켠 회원에게는 Cognito가 비밀번호 찾기 코드를 이메일로 보내지 않습니다 (MFA 코드와 복구 코드는 다른 통로여야 함, AWS 문서 확인). 위 **Reset password**도 코드를 메일로 보내므로 같은 이유로 막힐 수 있습니다 (*미검증*: 3단계 시험에서 확인). 이때는 관리자가 **임시 비밀번호**를 줍니다.

1. **본인 확인**: 요청이 회원의 **가입 이메일 주소**에서 `contact@quantgeneration.com`으로 온 것인지 봅니다. 다른 주소에서 온 요청이면 가입 주소로 다시 보내 달라고 답합니다.
2. **임시 비밀번호 만들기**: 13번 규칙(10자 이상, 숫자·소문자·대문자·특수문자)을 지키는 무작위 문자열. 같은 것을 두 번 쓰지 않습니다.
3. **설정**: CloudShell (Golden Hour Code 계정, 시드니)
   `aws cognito-idp admin-set-user-password --region ap-southeast-2 --user-pool-id <풀 ID> --username <회원 sub 또는 이메일> --password '<임시 비밀번호>' --no-permanent`
   → 회원 상태가 **Force change password**가 됩니다.
4. **전달**: 그 회원의 **가입 이메일로만**, `contact@`에서 답장으로 보냅니다. "7일 안에 로그인해 새 비밀번호를 정해 주세요" 문장을 함께 씁니다 (13번: 관리자 임시 비밀번호 7일 만료).
5. **회원에게 생기는 일**: 임시 비밀번호로 로그인 → 이메일 MFA 코드 → **새 비밀번호를 바로 정해야** 들어감 (AWS 문서: 다음 로그인 때 NEW_PASSWORD_REQUIRED). 7일이 지나면 다시 3번부터.
6. **기록**: 변경 기록에 `날짜 | 임시 비밀번호 발급 | 회원 sub | 본인 확인 방법` (비밀번호 자체는 적지 않음). 보낸 메일의 임시 비밀번호 부분은 회원이 바꾼 뒤 지웁니다.
- **확인 상태**: `admin-set-user-password`의 임시 동작 **확인** (AWS API 문서). Reset password가 이메일 MFA 회원에게 막히는지 **미검증**.
- **확인 상태**: **확인** (D11). **소유자 시험 대상** (부록 C).

## 7. 이메일 인증 메일(코드) 재발송

- **언제**: 회원이 "인증 코드가 안 와요"라고 할 때.
- **누를 순서**

| 회원 상태 | 할 일 |
|---|---|
| 스스로 가입, 코드 미입력 (**Unconfirmed**) | ① 먼저 웹 인증 화면의 **코드 다시 받기** (웹사이트 요청 ACC-2)를 안내합니다. ② 그래도 안 되면 관리자가 CloudShell에서 아래 명령 A |
| 관리자가 만든 계정 (**Force change password**) | CloudShell 명령 B (우리 운영에서는 거의 없음) |
| 이미 **Confirmed** | 재발송할 것 없음 (**확인**). 로그인 문제면 6절 |

명령 A (인증 코드 다시 보내기):
```
aws cognito-idp resend-confirmation-code \
  --client-id <웹 앱 클라이언트 ID> \
  --username <회원 이메일> \
  --region ap-southeast-2
```
명령 B (초대 메일 다시 보내기):
```
aws cognito-idp admin-create-user \
  --user-pool-id <풀 ID> \
  --username <회원 이메일> \
  --message-action RESEND \
  --region ap-southeast-2
```

- **화면에 남는 회원 값**: 명령에 넣은 그 회원의 이메일 1개. 결과로는 코드가 간 곳(가려진 이메일 형태)만 나옵니다 (출력 모양 미검증). 명령 줄은 CloudShell 셸 기록에 남으므로 끝나면 `history -c`를 실행합니다.
- **회원에게 생기는 일**: 새 코드 메일이 갑니다. 예전 코드는 쓸 수 없게 된다고 봅니다 (미검증).
- **주의**: ① 코드 문의가 여러 건이면 SES 문제일 수 있습니다 → 14절 차단 목록. ② **Confirm account**(3절)로 대신 확인해 주는 것은 이메일 주인 확인이 끝난 경우만.
- **확인 상태**: 콘솔 재발송 버튼 **미검증** (0.3표 7번). 명령 A·B **확인** (AWS CLI·API 문서).

## 8. 이메일 변경

- **언제**: 기본은 **회원이 직접** 웹 계정 페이지(ACC-5)에서 합니다. 관리자는 회원이 예전 메일함을 잃어서 스스로 못 할 때만.
- **누를 순서 (관리자가 대신)**
  1. 본인 확인을 먼저 합니다 (11절 2단계). 예: 가입 시각, 마지막 이용 시기 등 회원만 아는 것.
  2. 공통 경로 → **Users** → 회원 → **User attributes** 구역의 편집 버튼 (**Edit**, 미검증).
  3. `email` 값을 새 주소로 바꿉니다.
  4. **Mark email address as verified** (문구 미검증)는 **켜지 않습니다**.
  5. 저장 (**Save changes**, 미검증).
  6. 회원에게 "웹에서 새 주소 인증을 마쳐 달라"고 안내합니다.
- **회원에게 생기는 일**: 로그인 아이디가 새 주소로 바뀝니다. 인증 표시를 켜지 않았으므로 email_verified가 미인증이 되고, 새 주소 인증 전에는 비밀번호 찾기가 안 될 수 있습니다 (미검증). 회원이 스스로 바꾸는 경우에는, 새 주소 코드를 넣기 전까지 예전 주소로 계속 로그인됩니다 (풀 설정 "Keep original attribute value active when an update is pending", 문구 미검증).
- **주의**: 이메일이 로그인 아이디입니다. 잘못 바꾸면 남이 그 계정을 가져갑니다. 인증 표시는 본인 확인이 확실할 때만 켭니다.
- **확인 상태**: 편집 가능 **부분 확인**. 버튼·체크 문구 **미검증** (0.3표 2·3번).

## 9. 관리자 권한

"관리자"는 두 종류입니다.

| 종류 | 무엇 | 어디서 | 지금 실제 권한 |
|---|---|---|---|
| ① 웹 안의 관리자 표시 | 회원 계정을 `qg-admins` 그룹에 넣음 | Cognito **Groups** | **없음**. 서버가 없어서 그룹은 로그인 토큰의 `cognito:groups` 값일 뿐입니다. 나중에 웹 안 관리 기능이 생기면 쓰는 표시 |
| ② AWS 콘솔 관리 권한 | 회원 정보를 보고 바꿀 수 있는 사람 | AWS **IAM** | 이 문서의 모든 기능. 회원 계정과 무관 |

**① 그룹에 넣기·빼기**
- **언제**: 소유자 본인의 회원 계정을 처음 만든 뒤 1회. 그 밖에는 거의 없음.
- **누를 순서**
  1. 공통 경로 → **Groups** → **qg-admins**.
  2. **Add user to group** → 회원 선택 → 추가 (부분 확인).
  3. 빼기: 같은 화면 회원 목록에서 회원 선택 → 빼기 버튼 (**미검증**). 버튼이 없으면 CloudShell:
     ```
     aws cognito-idp admin-remove-user-from-group \
       --user-pool-id <풀 ID> --username <회원 이메일> \
       --group-name qg-admins --region ap-southeast-2
     ```
     (성공하면 아무것도 출력하지 않음. 화면에 남는 값: 그 회원 이메일 1개. 끝나면 `history -c`.)
- **회원에게 생기는 일**: 회원이 **다시 로그인해야** 새 토큰에 그룹이 반영됩니다. 지금은 화면상 변화 없음.

**② AWS 콘솔 권한**
- **권장: 다른 사람에게 주지 않습니다.** 1인 운영에서는 이것이 가장 안전합니다.
- 꼭 필요하면: 그 사람만의 로그인 (공유 금지), MFA 필수, 권한은 Cognito 회원 조회·정지 정도로 최소화, **부여·변경·회수의 날짜와 범위를 기록** (16.2절 권한 기록). 〔법률 자문이 아닙니다. 근거: 개인정보의 안전성 확보조치 기준의 접근 권한 관리 조항 (조문 번호와 기록 보관 3년은 **미검증**; 해설 URL 미확보, 원문은 https://www.law.go.kr 에서 확인 필요) · 2026-11-17 메인 D11 5.9절〕
- 이 계정은 AWS가 관리하는 조직 정책 아래라 IAM 사용자·역할 만들기가 막혀 있을 수 있습니다 (미검증).
- **매월**: `qg-admins` 구성원과 IAM 사용자 목록이 맞는지 봅니다 (16절).
- **확인 상태**: 그룹 동작(토큰 값, 다시 로그인 필요, 중첩 안 됨) **확인**. **Add user to group** 부분 확인. 빼기 버튼 **미검증**, 명령 **확인**.

## 10. MFA 강제

| 대상 | 누를 순서 | 회원에게 생기는 일 | 주의 |
|---|---|---|---|
| **관리자 본인 (AWS 콘솔 로그인)** — 가장 중요 | 이 계정은 IAM Identity Center 로그인입니다 (`OWNER_STEPS.md` 1-0). 액세스 포털 오른쪽 위 이름 → **MFA devices**에서 등록 여부 확인, 없으면 **Register device**. 관리자 경로: 관리 계정의 IAM Identity Center 콘솔 → **Users** → 본인 → **MFA devices** (AWS 문서 확인 2026-11-19) | 없음 | 콘솔이 뚫리면 모든 회원 정보가 위험합니다. 공개 전 체크 대상 |
| 회원 전체 | 공통 경로 → **Sign-in** → **Multi-factor authentication** → **Edit** → **MFA enforcement** 에서 **Require MFA** → 방법(인증 앱, 이메일) 선택 → 저장 | 켜는 순간 **모든 회원**이 다음 로그인 때 MFA를 설정해야 합니다 | 웹 로그인 화면이 MFA 설정 단계를 지원하기 전에 켜면 회원이 로그인을 못 합니다. **지금은 Optional MFA 유지** |
| 특정 회원만 | 콘솔에서 한 사람만 강제하는 방법은 찾지 못함 (미검증) | — | 회원에게 계정 페이지에서 켜도록 안내 |
| 이메일 MFA | Essentials 이상 + 자체 SES 필요 (**확인**). 우리 설정은 충족 | — | 메일함이 뚫리면 같이 뚫림 → 인증 앱 권장 |

- **언제**: 관리자 본인은 지금 바로. 회원 전체 강제는 유료 판매 등으로 위험이 커졌을 때 다시 판단.
- **확인 상태**: 회원 MFA 설정 경로 **확인**. 관리자 MFA 경로(IAM Identity Center) **확인** (AWS 문서, 2026-11-19).

## 11. 개인정보 열람·정정·삭제 요청 처리 (10일)

**기본 원칙**: 회원이 웹 계정 페이지에서 **직접** 할 수 있게 해 둡니다 (열람 = 내 정보 내려받기, 정정 = 이메일 변경, 삭제 = 회원 탈퇴, 동의 철회 = 소식 메일 끄기; 웹사이트 요청 ACC-5). 관리자는 회원이 스스로 못 하는 경우만 처리합니다.

- **언제**: 문의 메일함 `contact@quantgeneration.com` (개인정보 요청과 일반 문의를 함께 받음, 소유자 답 2026-11-18)으로 요청이 왔을 때.
- **누를 순서**

| 단계 | 할 일 |

## 12. 회원 정보 내보내기

콘솔에 회원 목록을 파일로 내려받는 버튼은 찾지 못했습니다 (미검증). CloudShell 명령으로 합니다.

- **언제**: 인증 안 한 계정 정리 목록 (16절 매주), 광고 수신자 목록, 사고 범위 파악 (17절).
- **누를 순서**
  1. 콘솔 위쪽 `>_` (**CloudShell**) 를 누릅니다.
  2. **화면에만 보기** (파일을 만들지 않음; 권장):
     ```
     aws cognito-idp list-users --user-pool-id <풀 ID> --region ap-southeast-2 \
       --query "Users[].{email: Attributes[?Name=='email']|[0].Value, status: UserStatus, enabled: Enabled, created: UserCreateDate}" \
       --output table
     ```
     화면에 남는 회원 값: **모든 회원**의 이메일·상태·사용 여부·가입 시각.
  3. **인증 안 한 계정만**: 2번 명령에 `--filter "cognito:user_status = \"UNCONFIRMED\""` 를 붙입니다. 화면에 남는 값: Unconfirmed 회원들의 같은 4칸. (필터 문법 **확인**: 속성 하나, `=` 또는 `^=`.)
  4. **광고 수신자만**: 사용자 정의 속성은 서버 검색이 안 되므로 전체를 받아 화면에서 거릅니다:
     ```
     aws cognito-idp list-users --user-pool-id <풀 ID> --region ap-southeast-2 \
       --query "Users[?Attributes[?Name=='custom:mkt_opt' && Value=='Y']].Attributes[?Name=='email']|[].Value" \
       --output text
     ```
     화면에 남는 값: 광고 수신에 동의한 회원의 이메일만. *(이 `--query` 식은 이 세션에서 실행해 보지 못했습니다 → 미검증. 결과가 비면 2번 명령에 `custom:mkt_opt` 칸을 더해 눈으로 거릅니다.)*
  5. **파일이 꼭 필요할 때만**: 명령 끝을 `--output json > users.json` 으로 바꿈 → CloudShell 오른쪽 위 **Actions** → **Download file** (미검증) → `users.json` → 일이 끝나면 내 PC 파일을 지우고, CloudShell에서 `rm users.json`.
  6. 끝나면 `clear`, `history -c`. 무엇을 왜 내보냈는지 16.2절에 한 줄.
- **회원 수가 많을 때**: `list-users`는 한 번에 최대 60명을 돌려줍니다. AWS CLI는 보통 다음 쪽을 자동으로 이어 받습니다 (미검증) → 결과 행 수와 풀 Overview의 회원 수를 비교합니다.
- **회원에게 생기는 일**: 없습니다.
- **주의**: ① 내보낸 파일도 개인정보입니다. 저장소·Notion·Drive·채팅에 올리지 않습니다. ② CloudShell 홈 폴더는 지우기 전까지 남습니다 (오래 안 쓰면 지워진다고 알려짐, 기간 미검증). ③ 필요한 칸만 뽑습니다.
- **확인 상태**: 콘솔 버튼 없음 **미검증**. 2·3번 명령 문법 **확인** (D11). 4번 식 **미검증**.

실제 사고면 KISA(국번 없이 118)에 먼저 전화로 묻습니다. 신고 화면의 위치는 미검증입니다.

### C. 대량 가입 (봇)

신호: `SignUpSuccesses` 경보 메일, SES 발송량 급증, 반송률 상승, 이상한 주소가 **Unconfirmed** 로 쌓임.

1. **자가 가입 잠시 끄기**: 공통 경로 → **Sign-up** → **Self-service sign-up** → **Edit** → **Enable self-registration** 체크 해제 → **Save changes** (**확인**). 기존 회원 로그인은 그대로 됩니다. 이 동안 웹의 가입 요청은 오류(NotAuthorizedException)를 받습니다 (**확인**).
2. 소유자를 거쳐 웹사이트 세션에 알림: 가입 화면에 "잠시 가입을 멈췄습니다" 문구 (플래그).
3. 가짜 계정 찾기: 12절 3번 명령 (Unconfirmed) + 가입 시각으로 범위를 정합니다.
4. 하나씩 확인하며 정지 → 삭제 (5절). 진짜 회원이 섞였을 수 있습니다.
5. SES 확인 (14절): 반송률이 5%에 가까우면 발송을 줄이는 것이 먼저입니다.
6. 재발 방지 (선택): 웹 가입 화면 CAPTCHA, 또는 Cognito에 AWS WAF 연결 (속도 제한). WAF는 월 $5 이상 (미검증), 연결 메뉴 위치 미검증.
7. 정리되면 1번 화면에서 다시 켭니다. 변경 기록에 남깁니다.

### D. SES 발송이 멈춤

가입 코드·비밀번호 재설정 메일이 안 갑니다 → 신규 가입이 사실상 멈춥니다.
1. SES **Account dashboard** 에서 상태 확인.
2. 원인 (반송·신고) 제거.
3. AWS 안내에 따라 재개 요청.
4. 그동안 소유자를 거쳐 웹에 안내 문구.

### E. 관리자 실수 (회원을 잘못 지움)

삭제는 되돌릴 수 없습니다. 회원에게 사실을 알리고 다시 가입을 안내합니다. 그래서 삭제 전 정지 단계(5절 2번)를 꼭 거칩니다. 풀 자체를 지우는 실수는 삭제 보호(0.3표 5번)가 막습니다 → 삭제 보호가 **켜짐**인지 공개 전에 봅니다.
