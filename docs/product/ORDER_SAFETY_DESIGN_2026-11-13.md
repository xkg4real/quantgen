# M-12 주문 기능 안전 설계 초안

상태: **문서 초안 작성. 주문 기능 미구현·실거래 비활성.**

이 문서는 소유자가 승인한 한도와 진행 순서를 구현 전에 대조할 수 있도록 정리한다.
완료 단위는 `M-12/design-draft/1`이며, 주문 기능이나 안전 설계의 최종 승인 완료를 뜻하지 않는다.
금액은 실제 계좌 자료가 아닌 승인된 기본값이다. 아래 계산 예시는 합성 자료다.

## 1. 근거와 진행 순서

- [소유자 판정 기록](../nautilus_bridge/OWNER_RULINGS_LOG.md)의
  **2026-11-11 P·A·B·C·D 묶음에 대한 답 "전부승인"**, P4와 D1~D14를 따른다.
  확인 기준은 main `795165cb45b6a37a6bf9bfc0ccd8cc6e6cb2acf0`이다.
- 같은 기록의 D 해석: 금액과 비율이 함께 있으면 **둘 중 작은 값**을 쓴다.
  수치는 실제 주문 자료로 검증한 결과가 아니다.
- `handoff/CURRENT.md`에 보존된 2026-11-12 Claude 인계는 안전 설계 **문서**를
  승인된 미착수 작업으로 넘겼다. 주문 모듈 구현과 안전 검사 변경은 **⑦-2 병합 뒤**다.
- 순서는 **문서 보고 → ⑦-2 이후 구현·안전 검사 변경 → 모의투자 → 결과 보고 →
  소유자의 실거래 전환 승인**이다. 모의 기록만으로 실거래가 자동으로 켜지지 않는다.
- D14에 따라 주문 기능이 든 버전의 배포는 서면 법률 의견 뒤다. 배포 실행은 별도 작업이다.
  [기존 배포 검토](DISTRIBUTION_REVIEW_2026-10-29.md)의 법률·자료 권리 미확인도 남는다.

이 문서의 **승인**은 위 판정 기록에 있는 내용만 가리킨다.
**설계 제안**은 구현 검토를 위한 안이고, **미확정**은 원문 확인 또는 결정이 더 필요한 부분이다.
초안의 병합으로 판정 기록, 기존 안전 검사, 소유자 승인 규칙을 바꾸지 않는다.

## 3. 한도 계산 예시

아래 `E`는 설명용 합성 계좌 평가액이며, 실제 구현에서 쓸 평가액 정의는 2절의 미확정 사항이다.
주문 한도는 허용 금액의 상한이다. 잔고·상품·시장·가격·기록 검사도 모두 통과해야 접수 후보가 된다.

| 합성 E | 1회 상한 min(100만, 5% E) | 하루 매수 상한 min(300만, 15% E) | 하루 손실 중지 min(40만, 2% E) | 종목 상한 min(400만, 20% E) |
|---:|---:|---:|---:|---:|
| 500만 원 | 25만 원 | 75만 원 | 10만 원 | 100만 원 |
| 2,000만 원 | 100만 원 | 300만 원 | 40만 원 | 400만 원 |
| 5,000만 원 | 100만 원 | 300만 원 | 40만 원 | 400만 원 |

예를 들어 E=500만 원에서 하루 매수 누계가 60만 원이면 남은 금액 상한은 15만 원이다.
1회 상한 25만 원 안이라는 이유로 20만 원 추가 매수를 허용하면 하루 한도를 넘는다.
보유액이 90만 원인 종목은 같은 평가액 기준으로 종목 한도 여유가 10만 원뿐이다.
이 예시는 미체결·비용을 0으로 둔 계산 설명이며, 실제 잔여 주문 가능 금액은 아니다.

실거래 첫 10거래일 한도 절반(D9)은 승인됐지만 일일 건수, 손실 중지, 기존 보유액 등
각 항목에 적용하는 방식은 여기서 새로 정하지 않는다. 확정 전에는 전환 조건 미충족으로 둔다.
가격 이탈의 **3% 초과**, 시세의 **15초 초과**와 임계값에 정확히 도달한 경우를 시험에서 분리한다.
참고가격을 정하기 전 임의의 계산식으로 실제 주문을 허용하지 않는다.

## 4. 모듈 경계와 확인 흐름 — 설계 제안

주문 기능은 연구 계산·원장과 분리된 하나의 경계 안에 두는 안이다.
외부 전송 권한은 그 경계의 어댑터에만 있고, 분석·전략·AI·예약 작업에서 호출할 수 없게 한다.
기존 연구와 TRADEGEN 경로 및 판정 기준은 이 설계의 변경 대상이 아니다.
폴더명과 API는 아직 결정하지 않았고, 이 문서에 실행 명령이나 키 설정은 넣지 않는다.

| 단계 | 필요한 입력·확인 | 실패 시 동작 제안 |
|---|---|---|
| 세션 열기 | 모의/실거래 모드, 허용 계좌, 서버·자격증명 일치, 거래일, 동기화된 내역 | 새 주문 잠금. 잘못된 모드나 알 수 없는 계좌로 대체 접속하지 않음 |
| 주문 작성 | 소유자가 직접 고른 상품·방향·수량·지정가, 계좌·현재 모드 표시 | 범위 밖 상품/금액·수량 형식 거부 |
| 첫 확인 | 예상 금액·비용, 잔여 한도, 보유/미체결, 시세 출처·시각, 주문 근거 표시 | 필수 자료 누락·오래된 자료·한도 위반이면 확정 화면으로 못 감 |
| 최종 확인 | 두 번째 명시적 확인, 동일한 주문 내용, 최신 한도·시세·세션 재검사 | 값이 바뀌면 첫 확인으로 되돌림. 화면에서 보던 주문과 다른 주문을 보내지 않음 |
| 전송 준비 | 고유 요청 식별자와 의도 기록을 먼저 보존하고 해당 주문의 한도를 원자적으로 예약 | 기록/예약 실패 시 전송하지 않음. 동시 클릭이나 다른 창의 중복 예약 차단 |
| 전송·조회 | 한 번만 전송한 요청의 접수·체결 상태를 증권사 식별자로 추적 | 응답을 잃으면 동일 주문을 자동 재전송하지 않고 접수 불명 상태로 유지 |
| 완료·대조 | 확정 응답과 체결·취소·정정 내역으로 상태 및 예약액을 갱신 | 확인되지 않은 주문을 완료/미접수로 추정하지 않음. 하루 대조 자료 보존 |

브로커의 중복 방지 기능이 있는지는 미확인이다. 앱의 요청 식별자만으로 서버 중복 방지가 된다고 주장하지 않는다.
다중 창·다중 프로세스·앱 재시작을 포함해 같은 계좌에 한 주문 작성자만 있게 하거나,
지속 저장소에서 예약과 상태 변경을 배타적으로 처리하는 방식을 구현 전에 선택한다.

## 5. 주문 상태와 중지 — 설계 제안

주문 상태와 세션의 주문 허용 여부는 따로 기록한다. 중지 버튼이 주문을 취소하거나 체결을 되돌렸다는 뜻은 아니다.

| 상태 | 의미 | 허용할 후속 처리 제안 |
|---|---|---|
| 작성 / 확인 대기 | 외부 전송 전 | 내용 수정 시 두 확인을 다시 받음 |
| 전송 준비 기록됨 | 요청 ID·내용·예약액은 저장했지만 외부 접수는 아직 미확인 | 재시작 시 증권사 조회로 확인. 기록만 보고 재전송하지 않음 |
| 접수 불명 | 요청 뒤 확실한 응답이 없음 | 조회와 사람이 확인하는 복구만 허용. 접수 여부 10초 미확인이면 D8 중지 조건 적용 |
| 접수 / 부분 체결 | 증권사가 확인한 주문이 열려 있음 | 중복·역순 통지를 식별하고 실제 확정 체결량만 반영 |
| 체결 완료 / 거절 / 취소 확인 | 증권사 근거로 종료를 확인 | 원본 사건 기록은 유지하며 누계·예약액 계산에 반영 |

취소나 정정 요청도 응답이 없으면 별도 미확인 상태다. 요청 성공과 취소·정정 완료를 혼동하지 않는다.
부분 체결은 취소할 수 없으므로 남은 수량의 취소 확인과 이미 체결된 수량을 따로 표시한다.
정정을 단순 취소+새 주문으로 구현하거나 예약액을 먼저 풀어 버리지 않는다.

**중지 상태 제안:** 새 주문을 막고 원인·발생 시각·미확인 요청을 표시한다.
시세 조회, 주문 상태 조회, 내역 대조는 계속할 수 있게 설계한다.
중지 중 취소를 허용하는 범위와 확인 절차는 별도 정의가 필요하며 자동 취소·자동 청산을 추가하지 않는다.
해제는 D7의 글자 입력과 D8의 자동 재개 금지를 지킨다. 원인 해소·기록 대조·권한 확인을 해제 조건으로 제안한다.
손실 중지(D3)는 다음 거래일의 명시적 확인 전까지 유지하며, 날짜 변경만으로 풀지 않는다.

| 조건 | 출처 구분 | 초안의 처리 |
|---|---|---|
| 접수 여부를 10초 안에 알 수 없음 | D8에 명시 | 중지. 자동 재전송·자동 재개 없음 |
| 앱 기록과 증권사 내역 불일치 | D8에 명시 | 중지. 불일치와 해결 근거를 보존 |
| D8 나머지 세 자동 중지 조건 | **원문 확인 필요** | 이름·임계값을 임의로 채우지 않음 |
| 지속 기록/한도 예약 저장 실패 | **설계 제안**, 승인된 D8 조건 수에 포함하지 않음 | 외부 전송 차단. 이미 전송됐는지 불명확하면 접수 불명으로 복구 |
| 모드·계좌·서버 불일치 또는 한도 계산 자료 부족 | **설계 제안**, 승인된 D8 조건 수에 포함하지 않음 | 새 주문 차단, 원인 표시 |

## 6. 기록·대조·자격증명 — 설계 제안

기록은 연구 시행 수나 연구 판정 원장에 쓰지 않는다. 실제 주문 감사 기록의 위치·보관기간·삭제 정책은
법률 및 보안 검토와 함께 확정하고, 이번 문서 작업에서는 어떤 실자료 저장소도 열지 않는다.

권장 기록안은 사건 ID, 요청 ID, 모드, 마스킹된 계좌 식별자, 상품·방향·수량·지정가,
소유자의 두 확인 시각, 시세 출처·시각, 한도 입력값·정책 버전, 예약 변화, 전송 시각,
증권사 주문 식별자·응답 상태, 부분 체결, 취소/정정 연결, 중지·해제 사유와 대조 결과다.
**D10 원문의 상세 기록안은 아니며 검토용 필드 제안**이다.
키·토큰·원본 계좌번호·응답 전체를 로그/오류 보고/공개 저장소에 넣지 않는다.

하루 한 번 대조(D10)는 주문·체결·취소/정정·잔고/보유의 범위, 자료 기준 시각,
차이 내역, 담당 확인, 해결 자료를 남기는 안이다. 자료가 없거나 일부만 수신되면 미대조로 남긴다.
한때 발생한 불일치를 해결했다고 과거 발생 횟수를 0으로 덮어쓰지 않는다.
오류 정정도 원 기록을 삭제하지 않고 연결된 후속 사건으로 남긴다.

모의·실거래 키와 계좌 설정은 D11대로 구분하고, 한쪽 값이 비었다고 다른 쪽으로 대체하지 않는다.
실거래 전환에는 별도 소유자 승인과 D7 입력 확인이 모두 필요하다.
저장·조회 권한, 암호화, 백업·복구, 로그 반출 범위는 구현 전 검토 대상으로 둔다.
